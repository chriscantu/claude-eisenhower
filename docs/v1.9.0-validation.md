# v1.9.0 Pre-Release Validation Checklist

Run these in a live Claude Code session against a real workspace before
tagging v1.9.0. Order = risk-descending. Stop at first failure, fix on
main, re-run from that step.

Mark each item with one of: ✅ pass · ❌ fail (note observed behavior) ·
⚠️ partial (note what worked / didn't).

---

## Tier 1 — Destructive paths (must validate)

These are the only `Write/Edit`-class commands that DELETE state. Bug
here = data loss for the user.

### 1.1 — `/forget all` confirmation gate strictness
- Run `/forget all` in a workspace with memory state present.
- Type literally `yes` → MUST NOT delete (token requires `forget all`).
- Type literally `forget` → MUST NOT delete.
- Type literally `forget all` → MUST delete glossary + people/ + 3 logs.
- TASKS.md MUST be unchanged across all three attempts.

### 1.2 — `/forget <alias>` partial-state behavior
- Run `/forget <real-alias>`. Type the alias verbatim to confirm.
- Verify glossary rows removed BEFORE people/ file unlinked (operation
  order biases to discoverable failure).
- Verify TASKS.md Delegated entries for that alias still appear (not
  touched).
- Confirm `/memory show <alias>` after the forget shows "no entries".

### 1.3 — `/forget task <title>` title-verbatim token
- Run `/forget task "<exact title>"` against a known memory row.
- Type literally `yes` → MUST NOT delete.
- Type literally the wrong title → MUST NOT delete.
- Type literally the exact title (case-sensitive) → MUST delete.

## Tier 2 — Schema + behavior changes

### 2.1 — `Awaiting:` field round-trip
- Add an Active task with `Awaiting: Security review` + `Check-by: 2026-06-05`
  to TASKS.md by hand.
- Run any command that touches the task (e.g., `/today`, `/status`).
- Verify the field survives and renders correctly.

### 2.2 — SCHEMA-010/011 validation
- Hand-write an Active task with `Awaiting: Vendor X` but NO `Check-by:`.
- Verify the next command that writes the record (or a tool calling
  `validateTaskRecord`) rejects it with `SCHEMA-010`.
- Repeat: hand-write a Delegated task with `Awaiting:` → expect
  `SCHEMA-011`.

### 2.3 — `/status awaiting` rollup
- Create 2+ Active tasks with different `Awaiting:` values + Check-by
  dates (one overdue).
- Run `/status awaiting`.
- Verify rollup grouped by blocker, overdue items flagged with ⚠️,
  business-day count matches Step 5 Risks computation.

### 2.4 — `/status` triage gate at threshold boundary
- Workspace with 4 tagged + 1 untagged tasks → `/status` MUST skip
  triage prompt.
- Add 1 more tagged task (now 5 tagged + 1 untagged) → `/status` MUST
  fire triage prompt.

## Tier 3 — New commands (additive)

### 3.1 — `/help` first-run vs returning
- Delete or empty TASKS.md (back it up first), run `/help` → walkthrough
  renders (Step 2A) + full command index.
- Restore TASKS.md with ≥1 task, run `/help` → walkthrough skipped (Step
  2B) + only command index.
- Verify all 13 commands appear in the index under correct lifecycle
  phase (Capture/Classify/Plan/Act/Reflect/Memory/Setup).

### 3.2 — `/trends` graceful degradation
- Delete all 3 `memory/*-log.md` (back up first), run `/trends` → "No
  analytics data yet" rendered.
- Restore. Run `/trends 1` → 1-week window honored.
- Run `/trends 60` → clamped to 52 weeks with clamp note in header.

### 3.3 — `/memory show` views
- `/memory` (no arg) → index lists aliases + log entry counts.
- `/memory show <known-alias>` → renders people/ file verbatim in a code
  fence.
- `/memory show analytics` → invokes `scripts/memory-analytics.ts`,
  parses JSON, renders three blocks.

### 3.4 — Diff surfacing on drift
- Construct drift: hand-edit memory/glossary.md to mark a Pending row as
  `Resolved — 2026-05-28` while TASKS.md still shows it Delegated.
- Run `/today` → drift surfaces in Section 1 with `⚠️ Memory:` prefix.
- Run `/status` → dedicated `─── ⚠️ Memory ↔ TASKS.md drift ───` block
  rendered after Risks, before Project sections.
- Revert hand-edit when done.

## Tier 4 — Scan-email count distinction

### 4.1 — `/scan-email` empty vs 0-matched
- Configured Apple Mail inbox with N>0 messages, NONE matching
  Admin/Compliance/VP/Survey patterns → output MUST include "Scanned N
  email(s); 0 matched the actionable patterns" with explicit count.
- Empty inbox → output MUST say "Your inbox is empty" (different
  wording).

## Sign-off

All Tier 1 + Tier 2 items pass → safe to release v1.9.0.
Tier 3 + Tier 4 failures → file follow-up issue, can ship v1.9.0
without them only if failure is cosmetic.

1. Move CHANGELOG `[Unreleased]` entries under `## [1.9.0] — YYYY-MM-DD`
2. Bump `.claude-plugin/plugin.json` version to `1.9.0`
3. Bump `scripts/package.json` version to match
4. `git tag v1.9.0 && git push origin v1.9.0`
5. `gh release create v1.9.0 --notes-from-tag`
